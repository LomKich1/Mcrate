## Что делаем
Десктопный плеер для Windows 11 на Rust. Играет музыку из Yandex Music, VK Music, SoundCloud и Spotify.
- Только клиент, своих серверов нет.
- Вход в сервисы по пользовательскому токену. Секреты и токены в код и в репозиторий не попадают никогда. Хранение: Windows Credential Manager (крейт keyring). В .gitignore уже есть .env, *.token, *.key, config.local.*.
- "Волна" как в Yandex Music. Сначала эвристика (лайки, пропуски, прослушивания, похожие треки из API сервисов), нейросеть только если появятся данные. Для Яндекса можно использовать его собственную волну через API.
- Интерфейс: чистый Rust-UI (не Tauri и не веб), аккуратный liquid glass, ориентир: проводник Windows 11. Блюр окна через системный механизм DWM (Mica/Acrylic, Windows 11 сборка 22621+), без костылей. Блюр внутри приложения рисуем сами шейдерами (wgpu). Экран настроек графики с детальной настройкой и полным отключением блюра. Конкретный UI-фреймворк ещё не выбран, выбираем под шейдерный блюр.
- Позже: встроенный AmneziaWG (или аналог с теми же конфигами), автогенерация конфигов с проверкой на основе конфигов Cloudflare WARP, плюс загрузка своего конфига. Желательно userspace-туннель только для трафика плеера, без драйвера TUN и прав администратора.
- Свои треки: пользователь может добавить локальные аудиофайлы (mp3, flac, ogg, wav, m4a и др. форматы, которые поддерживает symphonia/rodio; точный список проверим на практике). Добавление через drag&drop в окно (UI) и через выбор файлов/папки. Это провайдер LocalProvider наравне с остальными сервисами: без токенов, без сети.

## Подводные камни (учитывай)
- Официальных API у Yandex Music и VK Music нет, у SoundCloud новые приложения почти не регистрируют. Всё через неофициальные токены, может сломаться, нарушает правила сервисов.
- Spotify: официальный API только управляет воспроизведением. Звук локально возможен лишь с Premium и неофициальным librespot. Самый рискованный сервис, делаем последним.
- VK отдаёт зашифрованный HLS, Yandex подписывает ссылки на файлы. Проверяй актуальное состояние перед реализацией.
- boringtun (Rust-WireGuard) не умеет обфускацию Amnezia, скорее всего нужен amneziawg-go отдельным процессом. Лицензию проверить.
- Cloudflare WARP, насколько известно, поддерживает только часть обфускации (Jc/Jmin/Jmax). Проверять на практике.

## План по шагам
1. Cargo workspace: mcrate-core (общие типы, трейт MusicProvider: поиск, получение потока, лайки) и mcrate-app (окно, интерфейс, плеер).
2. Хранилище токенов (keyring) и экран подключения сервисов.
3. Провайдеры по очереди: Yandex Music, SoundCloud, VK, Spotify.
3a. LocalProvider: свои файлы (поиск по названию, чтение тегов, получение пути). Для него в mcrate-core добавляется ProviderKind::Local и StreamSource::LocalFile(PathBuf); менять общий интерфейс только после согласования вдвоём.
4. Звук: декодирование (symphonia) и вывод (cpal или rodio), HLS, буферизация.
5. UI: выбор фреймворка, Mica через DWM, блюр внутри приложения, настройки графики.
6. Волна (эвристика).
7. AmneziaWG и автогенерация конфигов.

## Правила работы вдвоём (ОБЯЗАТЕЛЬНО)

Работаем вдвоём в одной ветке main. Чтобы не затирать код друг друга, git-цикл соблюдаем всегда. Один из нас новичок в git, поэтому ты (Claude) обязан:
- в начале каждой рабочей сессии напомнить сделать `git pull`;
- после КАЖДОГО законченного изменения (новая функция, исправление, правка конфигов) сам напомнить про коммит и push и дать точные команды ниже;
- объяснять каждую команду простыми словами, не предполагать, что человек её знает;
- не давать пользователю продолжать работу, пока он не подтвердит, что push прошёл.

### Начало работы
git pull
(скачивает свежий код от напарника; делаем ВСЕГДА перед тем, как что-то менять)

### После каждого законченного изменения
1. cargo build
   (проверка, что код собирается; сломанный код в main не отправляем)
2. git status
   (смотрим, какие файлы изменены; если видишь .env, токены или ключи, СТОП и ничего не добавляем)
3. git add .
   (подготовить изменения к сохранению)
4. git commit -m "коротко, что сделал"
   (сохранить версию локально)
5. git pull
   (ещё раз подтянуть чужие изменения, пока ты работал)
6. git push
   (отправить свою версию на GitHub)

### Если что-то пошло не так
- Конфликт при pull (git пишет CONFLICT): остановиться, ничего не удалять, показать Claude полный вывод и разбирать по шагам.
- Никогда не использовать `git push --force` и `git reset --hard` без согласования с напарником: они стирают чужую работу.
- Коммиты маленькие, по одной задаче, чтобы напарнику было легко читать.
- Общие интерфейсы (трейты в mcrate-core) меняем только после согласования друг с другом.
- Новые решения (фреймворк, крейты) записываем в этот файл.
